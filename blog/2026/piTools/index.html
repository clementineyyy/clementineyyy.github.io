Pi Agent工具调用&skills源码深入解析

Created on November 14, 2026

2026   ·   agent-harnessing   ·   technology-stack

本文整理了本文结合Pi源码，详细分析了Pi工具调用&skills的方案设计、选择理由和实现细节。其中所有代码参考位置均对应笔者fork仓库，而非项目原始仓库。

工具定义

逐层定义工具的原因

第一层：给LLM看的Tool

// packages/ai/src/types.ts:433-437 export interface Tool<TParameters extends TSchema = TSchema> { name: string; // 工具名，如 “read”、”bash” description: string; // 给 LLM 看的工具描述 parameters: TParameters; // 参数的 JSON Schema（用 TypeBox 定义） }

第二层：执行工具的AgentTool

需要知道怎么执行这个工具、这个工具能不能并行执行、参数格式要不要预处理

// packages/agent/src/types.ts:371-394 export interface AgentTool<TParameters, TDetails> extends Tool<TParameters> // 继承 Tool 的三个字段 { label: string; // 给人看的标签，如”读取文件” (不同于给LLM看的name如”read”和description) prepareArguments?: (args: unknown) => Static<TParameters>; // 兼容性垫片，处理不同模型输出的参数怪癖 execute: ( // 真正的执行函数 toolCallId: string, params: Static<TParameters>, signal?: AbortSignal, onUpdate?: AgentToolUpdateCallback, ) => Promise\<AgentToolResult\<TDetails\>\>; executionMode?: "sequential" | "parallel"; // 标记这个工具能否和其他工具并行执行 }

第三层：更多能力的ToolDefinition

  • 可以加入更多功能如：工具自定义UI渲染/展示方式 (read工具在终端里怎么显示？edit工具怎么展示diff？)、提示词注入 (有些工具需要在系统提示词里加一段使用指南)
  • ToolDefinition的execute函数比AgentTool多了一个参数ctx: ExtensionContext，让工具执行时可以访问当前会话状态
  • ToolDefinition还新增了promptSnippet系统提示词片段、renderCall调用时渲染、renderResult结果时渲染等UI相关字段
  • 包装器函数把ToolDefinition变成AgentTool

怎么暴露工具？

一句话总结：根据一系列规则筛选工具，将其与历史system message累计的toolsAdded/toolsRemoved增量声明做差分得到的toolsAdded/toolsRemoved增量声明，再和历史system message总结出完整工具列表供LLM调用；LLM可工具搜索发现system message之外的工具并将其加入toolsAdded和system message中

为什么做增量？

Pi记录toolsAdded/toolsRemoved增量不是为了“直接把增量扔给模型当完整列表”，而是为了：

  • 把工具状态变更持久化到会话历史，供恢复、fork、tree navigation使用，并让能从历史中重放出当前完整列表
  • 发给模型时，根据模型不同，要么折叠成一条含完整列表的system message，要么把历史增量原样发给模型让模型自己重放
  • 增量比完整列表的优点：
    • 节省Token：如果一个session有50个工具，本次只新增1个，发toolsAdded: [{name: “new_tool”, …}] 只需几十token；如果每次都把完整列表重新塞进system message，每次请求都要重复发50个工具的定义，浪费大量 context
    • 表达定义变更：参考文件 packages/ai/src/utils/transcript.ts，getToolStateChanges() (150–167)。如果某个工具的description变了 (比如prepareLoadout钩子修改了描述)，该工具会被同时标记为toolsRemoved旧定义和toolsAdded新定义。模型看到这一对增删，就知道该工具的声明发生了变化。如果直接发完整列表，模型本轮可能无法对比出到底哪个工具的描述变了

区分2种工具范围

模型能调用的工具范围：agent.state.tools/context.tools (两者相同) $\neq$ 模型能直接看见的工具范围：system message 声明中的工具

  • context.tools字段不直接发给模型，这是给pi内部runtime用的经筛选后的可执行工具列表
  • system message是对话中role为”system”的一条消息，包括系统提示词和当前可用的工具声明，不是整个对话历史

LLM可见工具范围

工具经过一系列规则的筛选之后 (一开始提供所有非 deferred、允许模型调用的工具)，发给模型的是那条system message，里面是toolsAdded/toolsRemoved增量声明，它会被追加到对话历史中，而历史中的之前增量不会丢失。模型最终看到的是累积后的完整列表

具体讨论system message中的工具：

  • toolsAdded声明中出现的工具，模型看到的是完整工具定义 (name、description、parameters)，但工具原本的description可能被prepareLoadout钩子替换
  • toolsRemoved声明中出现的工具，模型只看到它的name，知道它被移除了，不再看到完整定义
  • 若工具被hiddenDeclarations隐藏，则根本不会出现在system message声明中，模型完全看不到它的定义
  • 工具定义变更、工具顺序变更都会修改toolsAdded/toolsRemoved增量，用户删除某个工具时候只会修改toolsRemoved增量，新增工具时只会修改toolsAdded增量

prepareLoadout钩子的2种用法：

  • 替换掉模型在system message里看到的该工具description，模型看到的不是原始定义，而是钩子返回的文本。这样可以在工具负载生效前，动态调整其他工具对模型展示的description，而不改动其参数parameters。典型用途：
    • 上下文相关的提示：根据当前会话状态，把某个工具的描述改得更具体，让模型更准确地判断何时调用
    • 命名空间说明：codemode工具可以在自己的description里列出当前可通过它调用的codemode工具列表，或者根据MCP服务器连接状态动态更新说明
  • 也可以把某些active工具放进hiddenDeclarations，让它们在system message声明中被隐藏，模型因此看不见、不知道它们的存在，虽然它们仍在agent.state.tools中 (active，可执行)。
    • 这意味着：模型可能完全不知道某个active工具的存在，因为它被hiddenDeclarations隐藏了；但该工具仍在agent.state.tools里，如果模型somehow调用了它 (比如通过tool_search动态加载后，不过tool_search也是可选工具，可能不激活且默认为false)，runtime仍能在context.tools中按名找到并执行

工具搜索tool_search

工具搜索的步骤：

  • LLM调用tool_search，传入查询词
  • 服务器使用BM25算法找到deferred==true且还没提供给LLM的匹配工具，把新工具写入this.agent.state.tools，并重建系统提示词
  • 下一次LLM请求前，把agent.state.tools与transcript中已声明的工具做差分，新加入的工具会出现在本次请求的system message toolsAdded增量中，LLM就能看到并调用它们

如何判断是否调用工具、调用哪个工具？

一句话总结：提示词设置和提示词注入钩子函数+由LLM决定是否调用工具、调用哪个工具 (和claude code不同，没有内置的 tool_choice/required/none等强制机制)

钩子函数通过提示词注入的方式提示LLM使用工具 (均默认不启用)： | 可选钩子 | 和工具调用相关部分 | 作用 | 注入内容来源 | | :—:|:—:|:—:|:—:| | transformContext | 在发给LLM之前，修改AgentMessage[]，可以插入/修改system或user消息，暗示LLM调用某工具 | 上下文管理：压缩旧消息、插入system提示词、过滤不适合发给模型的消息等 | 代码生成：可以是提前写好的静态字符串，也可以根据当前messages动态计算 (比如摘要之前的对话内容) | | prepareRequest | 每次provider请求之前，修改请求上下文或model | 替换请求的context、model、thinkingLevel，比如动态切换模型 | 代码生成 | | getSteeringMessages | inner loop开始、prepareNextTurn后、turn_end后，向队列插入消息 (例如一条user消息说“请调用XXX工具”)，由LLM再次处理 | 从steering queue取出待注入消息 | 通过agent.steer(message)入队，内容是运行时生成的 | | finishTurn | turn结束后，决定是否继续，可用于在特定条件下让循环继续，诱导后续工具调用 | 决定循环继续还是结束；不直接注入消息，只是控制流程 (默认不启用，只是用来干预/覆盖默认循环行为的可选钩子) | 代码决定{action:”continue”}或{action:”end”} |

如何判断工具能否真正执行？

agent能看到并生成某工具的调用，但因权限不足/参数类型不对或格式错误而不真正执行

核心在prepareToolCall，步骤如下：

step1. prepareArguments参数准备/兼容性垫片：不同模型的API在序列化工具参数时有微妙的差异；

step2. validateToolArguments做schema校验：prepareArguments 是”我知道某个模型会犯什么错”的兼容层，只处理特定模型的已知问题。validateToolArguments是”不管谁调我都得验”的安全层，保证参数类型正确；一个是兼容性，一个是正确性，混在一起会让代码很难维护

step3. config.beforeToolCall进行权限检查/拦截 (这是一个钩子接口，pi不默认实现，由开发者自行实现权限判断；因此在默认情况下，工具一旦出现在context.tools里，模型就能看到并生成调用)：如果钩子返回{block: true, reason: “危险命令”}，那么不会调用tool.execute，而是直接产生一条isError: true的正常的ToolResultMessage工具结果返回给模型；被block的调用会经历完整的生命周期事件 (tool_execution_start → tool_execution_end → toolResult)，只是isError为true，内容是拒绝原因；模型收到错误后可以自行决定重试、放弃或向用户说明；整个过程不会抛异常，不会打断循环

step4. tool.execute实际执行，定义如下：

execute: (toolCallId, params, signal, onUpdate) => Promise

其中四个参数：toolCallId是这次调用的ID，params是验证过的参数，signal是用于取消的AbortSignal (由用户按Ctrl+C时触发)，onUpdate解决”长任务的进度感知”问题 (工具执行事件很长时，能让工具能边执行边向外推消息，使工具执行可观察、可向用户实时汇报进度)

step5. afterToolCall钩子修改结果：

afterToolCall的应用场景

异常处理

不管哪一步出错，最终产物都是一条isError: true的ToolResultMessage；异常和消息的区别不在于”内容是什么”，因为两者描述的是同一件事，而在于接收者是谁：异常的接收者是调用栈/外层框架，它会打断循环；消息的接收者是模型，它会消化错误然后继续；Pi选择把异常翻译成消息，让”工具出错”成为模型可见的、可处理的正常信息流，让模型自己决定下一步该做什么 (重试/换路径/向用户解释)，比框架替它决定更好

把异常变成消息返回给模型

异常处理方式：

  • 异常被catch，不穿透：tool.execute()抛什么异常都会被catch接住，包括文件不存在的ENOENT、权限拒绝的EACCES、命令超时的TIMEOUT、JSON解析失败的SyntaxError
  • 异常被翻译成正常结果：catch块里调用createErrorToolResult(error.message)，把异常对象转成一个content里装错误描述文本、带错误标记的消息AgentToolResult
  • 进度事件先发完，再编码错误：catch块里的await Promise.all(updateEvents)保证工具执行过程中已经发出的tool_execution_update事件全部送达后，才发出错消息，否则事件乱序，UI会看到”工具先报错，再吐出最后一行进度”的诡异画面
  • 错误描述越具体，模型纠错能力越强：具体的错误描述等于给模型一份”怎么改才对”的提示；pi在工具内部就把错误描述写得很具体，能识别已知错误类型并包装成具体可读的描述；框架兜底层只在工具没识别出来时接管，把error.message原样透传给模型

ToolResultMessage返回工具调用结果

因为工具调用结果放在上下文中才能被LLM看到，不是直接把工具调用结果返回给LLM，所以要限制每次工具结果的长度，避免一份特别长的工具调用结果就占掉大量上下文空间；但是pi没有实现工具调用结果的截断策略，而claude code和codex都实现了

如何并行工具执行

模型返回几个tool_call是模型自己的决定，但这些调用是并行还是串行执行，由pi的全局toolExecution设置 (默认”parallel”并行执行)和各工具的ToolExecutionMode决定 (不是parallel就是sequential)，不是由LLM决定的。

  • 只有当全局配置是”sequential”，或者本轮某个被调用的工具自身声明了executionMode===”sequential”时，这一轮才退化为串行 (即只要这批工具中有任何一个声明了executionMode: "sequential"，整批都串行)；否则全部按并行处理
  • 保守的原因：因为判断哪些工具会冲突很难：edit和edit 操作不同文件就安全吗？万一它们编辑的文件有依赖关系呢？所以Pi选择了”宁可多等，不可出错”

具体实现并行

通过任务调度器scheduler管理所有任务的生命周期&状态转换+allSettled连接策略等待全部完成 (成功或失败都算)才汇总返回+每个tool_call一个独立任务、独立运行

tool_execution_end按完成顺序触发，但工具调用结果按照toolCallId调用的顺序，独立追加在上下文后面 (不会嵌套在一个返回消息中)，即工具调用结果ToolResultMessage的顺序和工具调用请求的顺序保持一致

串行模式：一个完全结束，才开始下一个

ToolCall A: 准备→验证→beforeHook→执行→afterHook→emit end

ToolCall B: 准备→验证→beforeHook→执行→afterHook→emit end

并行模式（三阶段设计）：

阶段1-准备 (顺序)：A准备→B准备→C准备

↑ 前置校验tool_execution_end 按完成顺序触发prepareToolCall含验证和beforeHook，必须顺序执行 (因为验证和权限检查不能并行，万一B被拦截了，C就不应该执行)

阶段2-执行 (只有实际执行并行)：A、B、C同时执行 (Promise.all)

↑ 只有tool.execute并行，省时间

阶段3-事件 (有序)：end按完成顺序发 (先完成的先发tool_execution_end)；ToolResultMessage按调用顺序发

↑ result消息保持和ToolCall一致的顺序，LLM收到的上下文才是正确的
